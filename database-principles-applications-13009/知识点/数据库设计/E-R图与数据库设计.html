一、数据库设计概述 ⭐

识记 数据库设计的特点与方法；领会 数据库设计的基本步骤。
数据库设计：根据一个部门的应用需求，设计出最优的数据库模式，建立数据库及其应用系统，有效存储数据，满足用户的信息要求和处理要求。
四个特点（简答/多选）：①是有结构（数据模型）和行为（应用程序）两方面的设计——既要设计数据库结构，又要设计与之匹配的应用程序，二者结合进行；②是一项综合技术，涉及计算机硬件、软件、数学、应用领域知识；③以需求为出发点、设计为核心（需求分析不当会导致整个系统失败）；④周期长、花费高，必须讲方法、有步骤、用工具。
常用方法：生命周期法（分阶段、按步骤）、原型法（先做出可运行原型再逐步细化）、E-R 方法（实体-联系方法，最常用、本章主角）、面向对象方法。实际设计中常杂交使用。
六个基本步骤（必须按序背，选择题常考顺序与各步任务/成果）：
  1. 需求分析——调查与理解：数据需求＋处理需求＋安全性与完整性要求。成果：需求说明书、数据流图 DFD、数据字典 DD。
  2. 概念结构设计——把需求抽象为独立于任何 DBMS 的概念模型。成果：E-R 图（概念模型）。
  3. 逻辑结构设计——概念模型转换为所选 DBMS 支持的数据模型并优化。成果：关系模式集合 + 用户子模式（外模式）。
  4. 物理结构设计——为逻辑模型选择存储结构与存取方法。成果：物理数据库定义（存储路径、索引、聚簇等）。
  5. 数据库实施——建库建表、装载数据、编程与调试、试运行。
  6. 数据库运行和维护——运行监控、性能监测与分析、重组与重构（阶段性修订扩张）。
🔑 记忆："需概逻、物实维"。前两布的差别是考点——概念设计的结果与机器/DBMS 无关，逻辑设计才开始"落地到某个 DBMS"。

二、需求分析：任务与方法

识记 需求分析的任务；领会 需求分析的方法。
任务：准确了解现实世界要"做什么"（而不是"怎么做"），包括信息要求（要处理和使用什么数据，导出对数据的需求）、处理要求（要完成什么处理功能与处理精度）、安全性与完整性要求。需求分析是最重要、最难、最需要与人沟通的一步，是设计开发的基础。
方法与做法：①建立数据流图（DFD）与数据字典（DD）——DFD 描述处理（外部实体、加工、数据流、数据存储四种符号），DD 描述数据（对数据项、数据结构、数据流、数据存储、处理过程的定义），二者互相配合构成需求规格说明；②需求调查方法：访谈、问卷、参加业务实践、查阅原有系统的档案与报表、召开调查会；③自顶向下逐层分解的结构化分析方式。
📝 数据字典是"关于数据的数据"（元数据），是需求分析的核心工具，也是后续设计、维护的共同依据；它一旦建立应集中管理、随时修改。

三、概念结构设计 ⭐⭐

识记 概念结构的含义；领会 概念结构设计的方法和步骤；简单应用 局部 E-R 模型设计；综合应用 全局 E-R 模型设计。
概念结构（概念模型）：将需求分析得到的用户需求抽象为信息结构——它是现实世界到机器世界的中间层，独立于具体的机器和 DBMS，易于向关系/网状/层次等各种数据模型转换，也易于与用户交流（因为用的是用户熟悉的实体与联系）。
为什么"概念设计"要单独一步（简答）：直接把需求转成关系模式不容易，且会把结构与具体 DBMS 捆死；先做概念设计可以①与用户沟通确认需求无遗漏；②逻辑设计简单明确（按规则机械转换即可）；③系统适应性强——换 DBMS 只需改逻辑设计，概念模型不变。
E-R 模型三要素与符号（画图必备）：
要素符号说明
实体 Entity矩形，内写实体型名客观存在并可相互区别的事物（可以是人、物、事、抽象概念）；实体型用实体名＋属性名描述，实体集是同一型实体的集合
属性 Attribute椭圆，虚线与实体相连实体拥有的性质。主码（键）属性在椭圆名下画一条横线；多值属性用双线椭圆；派生属性用虚线椭圆
联系 Relationship菱形，实线连接相关实体，边上标 1 / n / m实体型之间的关联。同一实体集内部也可有联系（如"领导-被领导"）
联系的类型（按参与实体集的个数与对应关系）：
类型含义典型例子
1 : 1两个实体集至多一对一，甲对应一个乙、乙也只对应一个甲一个班级只有一个班长，一个班长只带一个班；学生 ↔ 学籍卡
1 : n一方对应多方，多方中每个只对应一方一个一个科室有多名医生，一名医生只属于一个科室；部门—职工
m : n双方都可对应对方多个学生 ↔ 课程（选课）；作者 ↔ 图书
概念结构设计的方法与步骤（领会）：常用自顶向下、自底向上、逐步扩张、混合四种策略，其中最常用的是自底向上的 E-R 方法——先定义各局部应用的概念结构（局部 E-R 图，即用户视图/外模式），再把它们集成成全局概念结构。步骤：
  1. 抽象公共实体：确定实体类型、属性与主码。
  2. 确定实体类型之间的联系（含类型 1:1/1:n/m:n 与联系的属性）。
  3. 画局部 E-R 图：按需求中的每个视图（业务模块）单独画一张。
  4. 选择适当的中心实体／共同属性作为基准，逐步合并成初步全局 E-R 图（一次集成一个局部图）。
  5. 优化与消除冲突，得到最终全局 E-R 图。
集成时的三类冲突（多选/简答高发）：属性冲突（同一属性的类型、长度、取值范围或单位不一致，如"年龄"有的用整数有的用"年龄段"）；命名冲突（同名异义：不同意义取同名；异名同义：同一意义取不同名）；结构冲突（同一实体在各局部图中属性组成不同；同一对象在一处是实体、另一处是属性；实体间联系类型不一致，如 1:n 与 m:n）。
🔑 优化全局 E-R 图的四条标准：实体尽量少、联系尽量少、无冗余属性与联系（能由其他属性推出的属性应去掉）、结构合理易扩展。

四、逻辑结构设计：E-R → 关系模式 ⭐⭐

识记 逻辑结构设计的任务；领会 步骤；综合应用 E-R 模型向关系模型转换。
任务：把概念结构（E-R 图）转换为与选用的 DBMS 所支持的数据模型（此处即关系模型）相吻合的关系模式集合，并优化（规范化、调整）、为不同用户设计外模式（视图）、给出完整性与安全性控制定义。
步骤：①初始关系模式（按下面三条规则转换）；②规范化优化（用第 9 章方法，通常达到 3NF，删除冗余属性、合并等价模式）；③评价与调整（检查能否满足查询需求、是否有高效实现方式）；④设计外模式与安全完整性。
转换三条规则（背熟＋会写主码外码，综合题第 2 问的全部答案）：
转换对象规则结果
每个实体型直接转换成一个独立的关系模式；实体的属性＝关系的属性，实体的主码＝关系的主码科室、医生、病人各成一表
1 : 1 联系①合并到任意一端：把另一端的主码及联系自身的属性加入该端关系，作为外码；或②单独成一个关系：两端主码＋联系属性，两端主码的组合作主码通常合并（少一张表）
1 : n 联系必须合并到 n 端：把 1 端的主码和联系自身的属性一起加入 n 端的关系模式，该主码在 n 端是外码（若合并到 1 端会造成空值与冗余）科室(1) → 并入 医生(n)；医生(1) → 并入 病人(n)
m : n 联系必须单独转换成一个关系模式：各端实体的主码＋联系自身的属性为该关系的属性，各端主码的组合为该关系的主码，其中每个主码又是外码选课(学号, 课程号, 成绩)——学号、课程号组合为主码，各自是外码
📝 答题书写要求：转换结果一律写成"关系名（属性，属性，…）"，并在主码下画直线、外码下画波浪线（本页用 下划线 代直线、波浪线 代波浪线示意）。别忘了联系的属性要一起带走，这是最容易失分的地方。
⚠️ 三个高频错误：①把 m:n 联系硬塞进某一端（导致重复组，违反 1NF）；②1:n 联系合并到了 1 端（一个科室行要存多个医生）；③多对多联系建表时只写了一个主码（应为两端主码的组合）。

五、物理结构设计（识记）

识记 物理结构设计的任务。
任务：为已设计的逻辑模型选取最适合应用要求的物理结构（存储结构与存取方法），并给出完整的物理数据库定义。具体内容包括：
①确定数据库的存储记录类型、格式与存放次序；②确定数据的存放位置与存储结构（磁盘文件组织、聚簇、表空间、分区）；③确定存取路径与索引（在哪些列上建什么索引，见第 6 章）；④确定存储参数、自由空间与增长量；⑤评价物理方案——主要指标是存储空间开销、访问效率（响应时间）、维护开销三者权衡，常需折中（多建索引提速但占空间并加大维护代价）。
🔑 与逻辑设计的分界：逻辑设计决定"有哪些表、什么列、什么约束"；物理设计决定"这些数据怎么存在盘上、怎么找得快"。MySQL 中的对应物即存储引擎选择（InnoDB / MyISAM）、聚簇索引、二级索引、分区表。

六、综合例题：医院病房（考纲 · 题型举例）

综合应用 独立进行概念结构设计与逻辑结构设计——整卷综合题原型。
题目：某医院病房计算机管理系统需要如下信息：科室（科室名，地址，电话）、医生（工作证号，姓名，职称，年龄，科室名）、病人（病历号，姓名，性别，主治医生工作证号）。约束：一个科室有多名医生，一个医生只属于一个科室但可负责多个病人，一个病人的主治医生只有一个。 (1) 画出上述实体联系的 E-R 图（不必画实体属性）；(2) 转换成关系模式并指出每个关系模式的主码和外码；(3) 用 SQL 语句建立"科室"表。
  1. 辨析联系类型。科室 ∶ 医生 ＝ 1 : n（一个科室多名医生，一名医生只属一个科室）；医生 ∶ 病人 ＝ 1 : n（一名医生负责多个病人，一个病人只有一个主治医生）。两个联系都是 1:n ⇒ 都合并到 n 端，不需要额外的联系表。
  2. 画 E-R 图（矩形＝实体、菱形＝联系、边标 1/n；主码属性在椭圆内名下加横线）：
    本题两个联系都是 1:n，故不产生独立的关系模式（若出现 m:n 则必须单独成表）
    若题目要求不画属性，则只需画三个矩形＋两个菱形＋连线，并在靠近两端处标 1 与 n——务必标，标注缺失直接扣分。
  3. 转换为关系模式（1:n 联系把 1 端主码并入 n 端；直线＝主码，波浪线＝外码）：
    科室（科室名，地址，电话）
    医生（工作证号，姓名，职称，年龄，科室名）　——科室名是外码，参照科室(科室名)
    病人（病历号，姓名，性别，主治医生工作证号）　——外码，参照医生(工作证号)
    逐条核对：三个实体 → 三个关系模式；无 m:n 联系 → 无额外表；每个非主属性完全依赖于本表主码 → 均已达 3NF（这一句是第 9 章与本章的衔接点，写上更稳）。
  4. 写"科室"表的建表 SQL（用第 3 章语法＋第 7 章约束）： 
    CREATE TABLE 科室 (                       -- 也可用英文名 department，试卷允许中文表名
  科室名  VARCHAR(20)  NOT NULL,
  地址    VARCHAR(50),
  电话    CHAR(11),
  CONSTRAINT pk_dept PRIMARY KEY (科室名)   -- 实体完整性：主码非空且唯一
);
    若题目接着要求建"医生"表，则外键这样写（注意先建被参照表）： 
    CREATE TABLE 医生 (
  工作证号 CHAR(6) PRIMARY KEY,
  姓名   VARCHAR(20) NOT NULL,
  职称   VARCHAR(10),
  年龄   SMALLINT CHECK (年龄 >= 18 AND 年龄 <= 70),   -- 用户定义的完整性
  科室名 VARCHAR(20),
  CONSTRAINT fk_doc_dept FOREIGN KEY (科室名) REFERENCES 科室(科室名)
      ON DELETE RESTRICT ON UPDATE CASCADE   -- 参照完整性：不许删还有医生的科室
);
🔑 综合题四步得分点自查表：□ 联系类型（1:1 / 1:n / m:n）判断对不对并标注在图上；□ 实体的主码选对（题目里"科室名""工作证号""病历号"都是天然码）；□ 1:n 并到 n 端、m:n 单独成表；□ 每个关系模式主码画线、外码画波浪线；□ 建表语句里有 PRIMARY KEY，需要时补 FOREIGN KEY … REFERENCES。

七、本章速记小结

六条一句话：
  1. 六步走：需求分析 → 概念设计 → 逻辑设计 → 物理设计 → 实施 → 运行维护。
  2. 需求分析交两样东西：数据流图 DFD（管处理）＋数据字典 DD（管数据）。
  3. 概念设计＝画 E-R 图：矩形实体、椭圆属性、菱形联系，成果与 DBMS 无关。
  4. 集成会撞三类冲突：属性冲突、命名冲突（同名异义／异名同义）、结构冲突。
  5. 转换三条规则：实体各自成表；1:1 可并入任一端；1:n 并入 n 端；m:n 必须独立成表（主码＝两端主码组合）。
  6. 物理设计只管"存哪儿、怎么找得快"：存储结构、索引、聚簇，评价看空间／效率／维护三平衡。
📌 学 4 学时但分值不低：综合题（E-R 图＋转换＋建表）约 10～15 分。拿分技巧是把每一步都写出来——即使图有小错，转换规则与建表语句仍能独立得分。
