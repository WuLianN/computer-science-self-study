一、Hadoop 概述：由来·特点·生态体系（识记）⭐

识记 Hadoop 生态体系主要产品；领会 Hadoop 要解决的问题和应用场景。
是什么：Hadoop 是 Apache 开源的、基于Java 的分布式系统基础架构 / 并行计算框架，由 Doug Cutting 受 Google 三篇论文启发创建（GFS 2003 → HDFS；MapReduce 2004 → Hadoop MapReduce；BigTable 2006 → HBase）。它让用户无需了解分布式底层细节，就能开发可扩展的分布式应用，处理海量数据。
三大核心：HDFS（分布式文件系统，解决"存得下"）＋ MapReduce（分布式并行计算模型，解决"算得动"）＋ YARN（资源管理与调度，解决"资源怎么分"）。
主要优点（简答清单）：①高可靠性（按位存储与处理，多副本、故障自动恢复）；②可扩展性（可上千节点，PB 级）；③高效性（数据本地性、并行计算，速度快）；④低成本（运行在普通商用/廉价 PC 服务器集群上，开源免费）；⑤支持多种平台与生态组件丰富。
要解决的问题：单机存不下海量数据、算不动、扩容难、成本高、故障多——用"横向扩展 + 分布式存储 + 并行计算 + 副本容错"一次性解决。
生态体系主要产品（识记，能说出各自功能）：
HDFS 分布式文件系统MapReduce 离线并行计算YARN 资源调度Hive 数据仓库/HQLHBase 列式分布式数据库Pig 数据流语言ZooKeeper 分布式协调Flume 日志采集Sqoop 关系库↔Hadoop 搬运Avro 数据序列化Chukwa 集群监控Mahout 机器学习库Spark 内存计算Storm/Flink 流计算Oozie 工作流调度Kafka 消息队列
典型应用场景：海量日志分析、用户行为画像与推荐、ETL 与数据仓库、文本/图像/音视频等非结构化数据处理、搜索引擎、电信与金融风控、生物基因与天文数据处理。
⚠️ 常见错项：Hadoop 不适合低延迟实时查询（它面向高吞吐离线批处理）、不适合大量小文件（NameNode 元数据受内存限制）、不适合迭代式交互计算（每次都要读写磁盘，这类交给 Spark）。

二、Hive 数据仓库工具（领会 / 简单应用）⭐

领会 Hive 的特点、与数据库的区别；简单应用 Hive 的执行流程和编译器组成。
定义与特点：Hive 是基于 Hadoop 的数据仓库工具，把结构化的数据文件映射为一张数据库表，并提供类 SQL 的查询语言 HQL（HiveQL），本质是把 HQL 翻译成 MapReduce（或 Tez/Spark）任务在 Hadoop 上执行。特点：①使用面向分析的 SQL 风格，学习成本低；②数据存储在 HDFS、元数据存在 MetaStore（常用 MySQL）；③一次写多次读、面向批处理、延迟高；④不存储数据本身，只做模式映射（schema on read，读时确定模式）；⑤支持自定义函数 UDF/UDAF。
Hive 与（传统关系）数据库的区别（简答高频，5 条）：
比较项Hive传统数据库（MySQL/Oracle）
数据规模海量数据（TB/PB），可扩展到上千节点中小规模数据（GB 级），单机为主
数据存储数据存在 HDFS（元数据存 MetaStore）数据存在本地文件系统/块设备
计算/执行把 HQL 转成 MapReduce 分布式执行解释/编译执行 SQL，单机为主
用途数据仓库 / OLAP 离线统计分析OLTP 联机事务处理
延迟与事务延迟高、基本不支持事务（读多写少）延迟低、支持事务（ACID）
模式读时模式（schema on read）写时模式（先建表定约束）
执行流程（简单应用·按序答）：用户提交 HQL → Driver（驱动器） → 解析器/解释器（SQL Parser）把字符串转成抽象语法树 AST 并做语法/语义检查 → 编译器（Compiler）把 AST 编译成逻辑执行计划 → 优化器（Optimizer）做逻辑/物理优化（谓词下推、列裁剪、分区剪枝、Join 策略选择）→ 执行器（Executor）把逻辑计划转成物理计划（MR/Spark 任务 DAG）提交集群 → 结果返回用户。
编译器（Driver）四大组成（识记/简答）：解释器（SQL Parser）、编译器（Compiler）、优化器（Optimizer）、执行器（Executor）；配合元存储服务 MetaStore 与执行引擎工作。
🔑 记忆："解—编—优—执"四步，AST 与逻辑/物理计划是三步产物。名词解释"什么是 Hive"务必点出"把 HQL 翻译成 MapReduce"这一本质。

三、HBase 分布式数据库（领会 / 简单应用）⭐⭐

领会 传统数据库遇到的问题、table 与 region 的关系、-ROOT- 表和 .META. 表记录的信息与关系；简单应用 HBase 数据的逻辑存储模型。
（一）传统关系数据库遇到的问题（简答）：①海量数据写不进、存不下（单机磁盘与 IO 瓶颈）；②难以水平扩展（分库分表复杂、成本高）；③高并发读写与低延迟要求难以满足；④表结构（schema）僵硬，难以容纳稀疏、动态列与半/非结构化数据；⑤主从复制单点故障与可用性限制。
（二）HBase 是什么：是一个分布式、版本化、面向列（列族）的非关系型数据库，Google BigTable 的开源实现，底层跑在 HDFS 上，提供对海量数据的随机、可伸缩访问（强一致、按行键排序、支持百万列、稀疏存储、多版本）。
（三）table 与 region 的关系（必考）：一个 table（表）按行键（Row Key）字典序的行范围水平切分成多个 region；region 是 HBase 中分布式存储和负载均衡的最小单元；每个 region 由起始键、结束键与所属表唯一确定；region 过大时会自动分裂（split）成两个，并可被 RegionServer 迁移；一个 RegionServer 可服务多个 region，但一个 region 只属于一个 RegionServer。
（四）-ROOT- 表与 .META. 表记录的信息与关系（三层定位）：
层次记录什么说明
ZooKeeper节点 /hbase/root-region-server 记录 -ROOT- 表所在 RegionServer 的位置客户端唯一的查找入口，解决"第一层从哪找"
-ROOT- 表记录 .META. 表的 region 位置信息（哪台 RegionServer）本身只有一个 region，不会被分裂
.META. 表记录用户表所有 region 的位置（region → RegionServer 映射）可分裂为多个 region
用户表真正的业务数据由 region 承载，分布在多台 RegionServer
🔎 定位链：ZooKeeper → -ROOT- → .META. → 用户表 region（最多三次跳转）。客户端会缓存查询结果，之后可直接命中。这是"传统数据库 vs HBase 元数据管理"对比的标准答案。
（五）HBase 数据的逻辑存储模型（简单应用·必背四要素）：逻辑上是一个四维稀疏多维映射（Key → Value），由 行键 Row Key、列族 Column Family、列限定符 Column Qualifier、时间戳 Timestamp 唯一确定一个 单元格（Cell/Version）。要点：①列族在建表时定义，列限定符可动态增加；②同一行键的多个列族数据不保证跨行原子性（单行原子）；③只存非空单元格，所以是稀疏的；④每个单元格可保存多版本，按时间戳倒序，版本数由列族属性控制。

四、Pig 与 Pig Latin（识记 / 领会）

识记 Pig Latin 的数据组织形式；领会 Pig、Hive 和数据库的区别。
Pig 是什么：Pig 是 Hadoop 上的大规模数据流处理语言与执行框架，其语言叫 Pig Latin；它把脚本自动翻译成一系列 MapReduce 作业，让不熟悉 Java/MR 的开发者用较少的代码完成复杂数据分析。Pig 由客户端（编译器 + 优化器 + 执行器）与执行引擎组成，支持本地模式（Local，单机调试）与分布式模式（MapReduce）两种运行方式。
Pig Latin 的数据组织形式（识记·四种，由小到大）：
类型含义例子
原子 atom单个数值，最基本的单位（int/float/bytearray/chararray 等）3.14、"apple"
元组 tuple原子构成的有序集合，一条记录(apple, 3)
包 bag元组的无序集合，Pig 的默认数据结构{(apple,3),(pear,5)}
映射 map键 → 值的关联集合，键为字符串[{"a":(apple,3)}]
Pig、Hive 与传统数据库的区别（简答）：
维度PigHive传统数据库
定位数据流处理框架（ETL/多步分析）数据仓库工具（SQL 查询分析）联机事务处理 OLTP
语言Pig Latin（过程式、脚本、可嵌套）HQL（声明式 SQL）SQL
使用者数据工程师/分析师，擅长多步流水线熟悉 SQL 的分析人员应用开发者
底层翻译成 MapReduce翻译成 MapReduce/Tez/Spark单机执行引擎
数据规模海量、半/非结构化海量、结构化（HDFS 上的表）中小规模、结构化

五、ZooKeeper 分布式协调服务（识记 / 简单应用）⭐

识记 ZooKeeper 的设计目标；简单应用 ZooKeeper 集群五种角色及其功能。
是什么：ZooKeeper 是 Hadoop 的分布式协调服务（子项目），为分布式应用提供一致性的数据服务，把复杂易错的协调工作（选主、配置管理、命名服务、分布式锁、集群成员管理、监控）封装成简单可靠的原语与接口。
设计目标（识记·五条）：①最终一致性——客户端无论连接哪台服务器，看到的都是同一个数据视图（最重要特性）；②可靠性——消息一旦送达并成功，就被持久保存，故障恢复后仍能读到；③顺序性——客户端的更新按提交顺序依次完成（全局时序 + 局部时序）；④原子性——要么成功、要么失败，不留中间状态；⑤实时性/时效性——保证在一段时间内客户端能读到最新消息。
集群五种角色及其功能（简单应用·必背）：
角色数量功能读 / 写 / 参与投票
Leader（领导者）有且只有 1 个（选举产生）发起并处理投票、决议事务请求，更新系统状态，调度集群内各服务器，通过原子广播分发事务 Proposal读 ✔ / 写 ✔（唯一写入口）/ 投票 ✔（发起者）
Learner（学习者）多个跟随 Leader 同步数据的角色的统称，包含 Follower 与 Observer—（抽象类别，不单独部署）
Follower（跟随者）多个处理客户端非事务（读）请求，把事务（写）请求转发给 Leader；参与 Leader 选举投票与事务 Proposal 投票（过半写成功）读 ✔ / 写 ✘（转发）/ 投票 ✔
Observer（观察者）可选与 Follower 类似（读 + 转发写），但不参与任何投票、不参与选举；目的是扩展读能力、提高读取速度而不影响写性能（3.3.0 起新增）读 ✔ / 写 ✘（转发）/ 投票 ✘
Client（客户端）任意请求发起方；与任一 Server 建 TCP 长连接（默认 2181 端口），发送请求与心跳，接收响应与 Watch 事件；连接断开会自动重连其他服务器并重建会话发起读/写请求
🎯 高频辨析：Follower 与 Observer 的唯一区别 = 是否参与投票（选举与写 Proposal）。要"高可用"靠 Follower，要"再加读性能"用 Observer。数据模型：ZNode 树形命名空间（像文件系统的目录，既可当目录又可存数据），类似 Unix 文件系统。

六、资源管理与调度 YARN：三种调度器（领会）⭐

领会 三种常见调度器的调度原理。
YARN 是什么：Hadoop 2.0 引入的通用资源管理系统与调度平台，把 JobTracker 的"资源管理 + 任务调度/监控"拆开，实现资源管理与计算框架解耦，让 MR、Spark、流计算等多框架共享一个集群。核心组件：ResourceManager（全局资源与调度）、NodeManager（单节点资源与容器管理）、ApplicationMaster（单个应用的申请、任务调度与进度上报）、Container（资源抽象单位：内存/CPU）。
三种常见调度器的调度原理（简答/对比必背）：
调度器调度原理特点 / 适用
FIFO
（先进先出）		作业按提交顺序进入队列，队首作业优先独占集群资源，前面的资源申请完后面的只能等待实现最简单、无并发队列；小作业可能被大作业长时间阻塞，只适合单用户/测试环境
容量调度器
Capacity Scheduler		把集群资源按配额（容量比例）划分给多个租户队列，每队有保证容量 + 最大容量；本队列空闲时允许借用其他队列的空闲资源，资源紧张时按容量归还面向多租户共享大集群，兼顾吞吐与利用率（Yahoo 主导）
公平调度器
Fair Scheduler		让所有作业公平共享资源：按权重与"已用资源"排序动态分配，新作业可抢占超额的作业资源，空闲资源被平均/按权分享保证没有作业饿死、小作业快速拿到资源（Facebook 主导）；适合作业大小差异大的多用户场景
🔑 一句话区分：FIFO 看"先来后到"，容量看"配额划分 + 可借用"，公平看"人人有份 + 可抢占"。另需知道 YARN 相比 MR1 的改进：把 JobTracker 拆成 RM 与 AM，降低了 JobTracker 压力、支持多计算框架、扩展性更好。

七、本章速记小结与自测

  1. 三大核心：HDFS 存、MapReduce 算、YARN 调度；Hadoop 源于 Google GFS / MapReduce / BigTable 三篇论文。
  2. Hive = 把 HQL 翻译成 MapReduce 的数仓工具；与数据库差在存储位置、执行方式、用途（OLAP vs OLTP）、延迟与事务、读时模式；编译器四件：解—编—优—执。
  3. HBase = BigTable 开源实现、面向列族的 NoSQL；region 是最小分布与负载单元；定位链 ZK → -ROOT- → .META. → 用户表；逻辑模型四要素 行键·列族·列限定符·时间戳。
  4. Pig 用 Pig Latin 写数据流，四种数据组织 atom / tuple / bag / map（bag 是默认结构）。
  5. ZooKeeper 设计目标五条（最终一致、可靠、顺序、原子、实时）；五角色 Leader / Learner / Follower / Observer / Client，Follower 与 Observer 只差"是否投票"。
  6. 三种调度器：FIFO 先来后到、容量按配额可借用、公平按权可抢占。
