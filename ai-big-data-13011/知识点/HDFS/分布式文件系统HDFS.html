一、DFS 的由来（识记 / 领会）

识记 分布式文件系统 DFS 的概念和主流产品；领会 产品选择因素、文件系统发展三个阶段。
DFS 概念：分布式文件系统（Distributed File System）是指管理的物理存储资源不直接连接在本地节点上，而是通过计算机网络（多台服务器）访问的文件系统；它把文件分散存储在多台机器上，对用户屏蔽底层差异，提供统一的命名空间与访问接口。
文件系统发展的三个阶段（领会）：
阶段形态特点局限
① 本地文件系统单机的 FAT、NTFS、ext4数据与计算在同一台机器，直接访问磁盘容量与性能受单机限制，无法共享
② 网络文件系统NFS、SMB/CIFS通过网络协议访问远端共享目录，集中存储服务器单点瓶颈，难扩展到海量
③ 分布式文件系统GFS、HDFS、Ceph、Lustre数据分块分散到大量节点，副本容错、横向扩展一致性弱（多为最终一致）、小文件不友好
主流产品（识记）：Google GFS（开创者，闭源）、Hadoop HDFS（GFS 的开源实现，最常用）、Lustre（高性能计算/科研）、GPFS（IBM Spectrum Scale）、Ceph（统一存储：对象/块/文件）、TFS / FastDFS（互联网小文件与图片）、MogileFS、GlusterFS、Alluxion/Alluxio（内存层）。
选择分布式存储产品时要考虑的因素（领会·6 条）：①容量与扩展性（能否在线扩容到 PB/EB）；②性能（吞吐、IOPS、延迟，是否匹配业务读写比）；③可靠性与可用性（副本/纠删码、故障自愈、SLA）；④一致性模型（强一致还是最终一致）；⑤成本（硬件、运维、许可）；⑥生态与兼容性（能否与 Hadoop/Spark/K8s 等工具链配合）；另可加上安全性（权限、加密、审计）与对文件大小与类型的适应能力。
⚠️ 单选陷阱：HDFS 是一次写入、多次读取（write-once / stream access）的文件系统，不适合低延迟随机访问、不适合大量小文件（每个文件/块都要在 NameNode 占约 150 字节的元数据，内存是瓶颈）、不支持文件随机修改（只能追加 append）。

二、设计思想：分而治之 · 目标 · 策略（识记 / 领会）⭐

识记 HDFS 的核心设计思路"分而治之"；领会 设计目标与主要策略；简单应用 HDFS 解决各类问题的方法。
核心设计思路——"分而治之"：把大文件切分成固定大小的数据块（Block）分散存储到多台数据节点上（"分"），再由名字节点统一保存元数据并调度、把结果汇总成完整文件（"治"）。一句话：存储上分块分散、管理上集中调度、可靠性上多副本冗余。
设计目标（领会·必背 7 条）：
#设计目标HDFS 的解决策略 / 实现方法（简单应用对应表）
1兼容廉价（低成本）硬件，运行在普通商用服务器上组件故障是常态而非异常 → 每个块默认 3 副本 + 机架感知放置 + 自动检测与重建副本
2流式数据访问（streaming access）面向批处理与高吞吐而非低延迟：一次写入、多次读取，允许追加，优化顺序读，用数据本地性减少网络传输
3大规模数据集（GB～PB 级、上千万文件）块式存储 + 元数据与数据分离；NameNode 只存元数据，数据分散到 DataNode
4简单的一致性模型"写前读"（read-after-write）强一致：文件写完才对所有人可见，简化编程模型
5跨平台可移植性纯 Java 实现，可在不同操作系统与硬件间部署
6高容错性副本丢失自动恢复、数据校验和（checksum）检测损坏并读另一副本
7高吞吐量 + 低成本并行读写、就近计算（把计算移到数据所在节点）
主要策略（关键词版，简答好写）：①分块存储（Block 化）；②元数据与数据分离、元数据集中管理；③多副本冗余 + 机架感知；④心跳与健康检查；⑤数据本地性 / 移动计算而非移动数据；⑥流式访问、追加写。
🔑 "分而治之"在答题时要拆成三句：大文件切块（分）→ 块分布到多节点并行读写（快）→ NameNode 统一管元数据并调度副本（治）。

三、HDFS 架构与数据块（识记 / 领会 / 简单应用）⭐

识记 HDFS 架构的结构及组成；领会 数据块的设计及其优点；简单应用 描述 HDFS 整体架构图。
HDFS 整体架构（"简单应用：架构图描述"按此六要素作答）
架构组成与职责（识记·六件套）：
组件数量职责
NameNode（名字节点 / 主节点）1（HA 下多活备）管理文件系统命名空间（目录树）与访问权限；维护文件↔数据块映射、数据块↔数据节点映射；元数据常驻内存，并持久化到 FsImage + EditLog；负责副本管理、调度与心跳监控
DataNode（数据节点 / 从节点）多台真正存储数据块（Block）；执行客户端的读写请求；按 NameNode 指令创建/删除块、复制块；定期发送心跳与块报告
SecondaryNameNode（检查点节点）1定期合并 FsImage 与 EditLog 生成新 FsImage（检查点），防止 EditLog 过大、缩短重启时间；不是热备
Client（客户端）任意向 NameNode 申请元数据，与 DataNode 直接通信完成文件的实际读写，切分文件为块并挑选数据节点
Block（数据块）海量HDFS 最小的存储与读写单位；Hadoop 1.0 默认 64 MB、2.0 默认 128 MB；文件不足一块按实际大小存
副本（Replication）默认 3放置策略：第 1 副本在本机/就近、第 2 副本在不同机架、第 3 副本在第 2 副本同机架的另一节点（跨机架容错 + 减少机架间流量）
为什么用"块"设计？块大小的取舍（领会）：块是与磁盘块无关的逻辑概念。块太大 → MapReduce 中每个任务处理的数据多、并行度低、传输等待久；块太小 → 元数据暴涨（NameNode 内存吃紧）、寻址与网络开销占比高、磁盘寻道时间超过传输时间。所以取一个"足够大以让传输时间远大于寻址时间"的折中值（128 MB）。
数据块设计的优点（简答）：①简化存储管理（块大小固定，元数据量小，NameNode 只需在内存中保存少量元数据）；②文件可以超过单机容量，块可分布到任意节点；③便于复制与负载均衡（以块为单位跨节点搬迁、均衡副本）；④便于容错（块损坏可按副本恢复）；⑤支持跨平台（块与底层文件系统解耦）。
⚠️ 高频考点：NameNode 内存限制了文件/块总数（约每个对象 150 字节）；元数据丢失 = 整个文件系统不可用，所以要 FsImage+EditLog 持久化、SecondaryNameNode 做检查点、生产环境配 HA（多 NameNode + JournalNode + ZooKeeper 选主）。

四、主要流程（一）文件与目录操作（综合应用）

综合应用 客户端与名字节点之间的文件与目录操作。
核心规律：所有"文件/目录操作"都是客户端 ↔ NameNode 的元数据交互，不碰真实数据；只有"读/写文件内容"才与 DataNode 通信。
操作流程要点
创建文件 / 目录Client 请求 NameNode → NameNode 在目录树中登记新节点（元数据）并检查权限/是否重名 → 返回成功；此时还没有数据块，块在写入时才分配
列出目录 / 查看属性Client → NameNode 查询命名空间 → 返回该目录的子项与元数据（大小、权限、副本数、块列表）
重命名 / 移动仅修改 NameNode 中的目录树结构（元数据），数据块不需要移动 → 所以 HDFS 的 rename/mv 是常数时间的轻量操作
删除文件NameNode 把该文件移入回收站（.Trash）或删除元数据 → 异步通知相关 DataNode 删除对应块；回收站保留期内可恢复（fs.trash.interval）

五、主要流程（二）读文件与写文件（综合应用）⭐⭐

综合应用 读文件、写文件的主要流程。
（一）读文件流程（7 步，按序背）：
  1. 客户端调用 DistributedFileSystem.open() 向 NameNode 请求读取文件。
  2. NameNode 校验权限后返回该文件的块列表及各块的副本所在 DataNode 列表（并按网络拓扑/机架距离排序，就近优先）。
  3. DistributedFileSystem 返回 FSDataInputStream，其底层 DFSInputStream 保存着块位置信息。
  4. DFSInputStream 连接距离最近的那个 DataNode，开始逐块读取数据（块内流式读取）。
  5. 当前块读完 → 断开该 DataNode 连接，再为下一个块寻找最近的 DataNode 连接读取。
  6. 若读取过程中发生通信错误：关闭该连接，把该块位置标记为不可用，从另一个副本重新读取，并把错误报告给 NameNode（触发校验与修复）。
  7. 所有块读完后，客户端关闭输入流；读的过程中客户端与 NameNode 不再交互（元数据一次性拿全）。
（二）写文件流程（7 步，注意"管道"与"确认反向传递"）：
  1. 客户端调用 DistributedFileSystem.create()，NameNode 检查权限、在命名空间登记新文件（状态为"正在创建"）。
  2. 客户端把文件切分成块，向 NameNode 申请为每个块分配 DataNode；NameNode 按副本放置策略返回一组 DataNode（如 3 个）。
  3. DFSOutputStream 与这些 DataNode 建立数据管道（pipeline）：客户端 → DN1 → DN2 → DN3。
  4. 客户端把数据以 packet（包）为单位写入管道，写入 data queue；DN 收到后转发给下一个，并写入本地磁盘。
  5. 每个 DataNode 写成功后向上游返回 ACK 确认，确认信息沿管道反向逐级回传，最终进入 ack queue；收到全部确认后客户端才认为该包写入成功（保证一致性）。
  6. 若写入过程中某个 DataNode 失效：①管道中失效节点之后的数据重新分配到其他节点；②把该节点从管道中移除；③该块副本数减少，NameNode 会在别处异步补齐副本；④把失效节点上已写的数据记录到别处，保证块完整。
  7. 客户端写完调用 close() → 通知 NameNode，等待所有块都已复制到位（达到最小副本数）后，文件才正式可用（"写前读"强一致）。
🎯 读 vs 写三处关键差异（简答对比题）：①读是"就近选副本、块间独立"；写是"建管道、包级确认"。②读出错→换副本继续；写出错→剔除节点 + 事后补副本。③读期间不再问 NameNode；写每块都要向 NameNode 申请分配节点、结束时要 close 确认。

六、主要流程（三）数据节点启动与心跳（综合应用）

综合应用 数据节点的启动和心跳流程。
启动与注册：DataNode 启动 → 扫描本地磁盘上的块文件与元数据，在内存中构建"块 ↔ 存储位置"映射 → 向集群中所有 NameNode 发起注册（register），上报自身标识（storageID）、主机与端口、资源使用情况 → 注册成功后进入服务状态。
心跳与块报告（三个周期，数字要记）：
机制周期内容与作用
心跳 heartbeat默认每 3 秒向 NameNode 报告"我还活着"，并携带容量使用、读写队列长度、统计信息；NameNode 的回复中携带指令（复制块、丢弃块、刷新缓存等）
块报告 block report启动时立即全量上报，之后默认每 6 小时一次上报本节点存储的全部块列表，NameNode 据此核对元数据与实际副本是否一致（副本缺失/多余的判定依据）
失效判定10 分钟 + 30 秒（10×心跳超时时间 + 30s）收不到心跳NameNode 判定该 DataNode 失效：把它上面的块标记为不可用 → 在其他节点复制补齐副本，保证副本数与数据可用性
🔑 记忆串："注册 → 3 秒心跳 → 6 小时块报告 → 超时 10 分半判死 → 自动补副本"。这也是 HDFS "把故障当作常态"设计目标的直接体现。

七、异构存储（识记）

识记 HDFS 支持的存储介质和存储策略。
背景：早期 HDFS 只认"磁盘"这一种介质，热数据与冷数据混放，成本高、性能浪费。Hadoop 2.4 起引入异构存储（Storage Policy / Type），允许按介质类型为不同数据选择存放位置，实现性能与成本的分级平衡。
支持的存储介质类型（Storage Type）：RAM_DISK（内存盘）、SSD（固态硬盘）、DISK / DEFAULT（普通磁盘）、ARCHIVE（归档介质，如磁带/高密度盘）、PROVIDED（由外部/下层提供）、COLD（冷介质）、WARM（温介质）、HOT（热介质）。
六种存储策略（识记·名称 + 一句话）：
策略含义适用
LAZY_PERSIST 延迟持久先写内存盘，由 DataNode 异步定期刷写到磁盘；内存盘不可用时退化为普通磁盘写高频小写、临时数据、加速中间结果
ALL_SSD 全 SSD所有副本都放 SSD，放不下才回退磁盘低延迟热点数据
ONE_SSD 一副本 SSD至少一个副本在 SSD，其余普通磁盘（默认策略的加强版）兼顾性能与成本的常用折中
TOP 分层（原 DEFAULT）按机架拓扑优先分布副本（同机架少跨、跨机架容错），介质不限通用默认
WARM / COLD 温冷部分/全部副本放 ARCHIVE 归档介质，热介质只留少量或不留历史数据、备份、合规留存
配套能力：①Move 命令（hdfs storagepolicies / mv）可把块在不同介质间迁移而不改数据内容；②缓存管理（Cache Directives / Alluxio 类）把热点数据常驻内存；③策略可按目录设置并被子目录继承。

八、擦除码技术 EC（领会）

领会 擦除码（Erasure Coding）的概念、原理和优缺点。
概念：擦除码是一种数据冗余与容错编码技术（纠删码）：把 k 个数据块通过编码生成 m 个校验块，共 n = k + m 个块分散存储；当任意 ≤ m 个块丢失时，都能用剩下的 k 个块 + 编码关系重建出丢失的数据。Hadoop 2.3 起在 HDFS 中支持 EC（Reed-Solomon 码）。
原理（以 RS(6,3) 为例）：把数据切成 6 个数据块 d₁…d₆，用 Reed-Solomon 矩阵算出 3 个校验块 p₁…p₃，共 9 个块放到 9 个不同节点/机架。任意 3 个块损坏（无论数据块还是校验块）都能由剩余 6 个块解方程恢复。HDFS 中 EC 以块组（block group，策略文件）为单位管理，写入时先填充 k 个数据块再算校验块。
优点：①大幅降低存储开销——3 副本需 300% 空间，RS(6,3) 只需 150%（1.5 倍），冷数据甚至可用 RS(10,4)=140%；②容错能力不降甚至更强（可容忍同时坏 3 个块）；③省下的就是成本，适合海量、写一次读多次的冷数据/归档数据。
缺点：①重建代价高——恢复一个丢失块要读取 k 个块并做计算，网络与 CPU 开销远大于"直接复制一个副本"；②不适合小文件（不足 k 个块无法发挥优势，反而增加元数据与复杂度）；③不适合频繁更新/随机写（编码需整块组重算）；④读取需跨更多节点，可能降低读吞吐、增加延迟；⑤配置复杂，需为目录显式设置 EC 策略文件，且不能与多副本策略随意混用。
⚖️ 一句话对比：3 副本 = 用 3 倍空间换"简单快速的重建"；擦除码 = 用 1.5 倍空间换"更高的存储效率但更贵的重建"。冷热分层：热数据用副本（或 ONE_SSD），冷数据用 EC + ARCHIVE。

九、本章速记小结

  1. 由来：本地 → 网络（NFS）→ 分布式（GFS/HDFS）；选型看容量、性能、可靠、一致、成本、生态六因素。
  2. 核心思想：分而治之——切块分散存、NameNode 集中管、多副本保可靠。
  3. 架构六件套：NameNode、DataNode、SecondaryNameNode（不是热备）、Client、Block（128M）、副本（默认 3、跨机架）。
  4. 三条流程：读（就近副本、块间独立、出错换副本）；写（管道 + packet + ACK 反向确认、节点失效则剔除并补副本）；心跳（注册 → 3s 心跳 → 6h 块报告 → 10 分半判死）。
  5. 块设计的收益：元数据少、可超单机、便于负载均衡与容错、跨平台。
  6. 异构存储：介质 RAM_DISK/SSD/DISK/ARCHIVE；策略 LAZY_PERSIST / ALL_SSD / ONE_SSD / TOP / WARM / COLD。
  7. 擦除码：k 数据 + m 校验，坏 ≤m 可恢复；省空间（300%→150%）但重建贵、不适合小文件与频繁写。
🎯 6 学时分配：①由来 + 设计思想 1 学时；②架构与块（对着 SVG 默画一遍）1.5 学时；③读写与心跳流程 2 学时（综合应用主战场，必须能分步书写）；④异构存储 0.5 学时；⑤擦除码 1 学时。本章整章考、无跳过节。
