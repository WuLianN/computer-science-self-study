一、设计思想：Mapping 与 Reducing（领会）⭐

领会 Mapping 与 Reducing 的涵义；MapReduce 设计思想的三个方面。
名字来源：MapReduce 借用了函数式编程语言（LISP）中的两个操作：Map（映射）与Reduce（归约/化简），由 Google 于 2004 年提出，是一种分布式并行计算模型/编程框架。
两个操作的涵义：Mapping（映射）——把一批数据用同一个函数进行转换，输入一组 <key, value> 键值对，输出一组中间键值对（"分解 + 转换"，各元素独立、可并行）；Reducing（归约）——把同一 key 的一组 value 汇总成一个（或几个）结果（"合并 + 聚合"，如求和、计数、求最大最小）。
设计思想的三个方面（简答必背）：
  1. "分而治之"（Divide and Conquer）：把大问题拆成可并行的 Map 任务处理，再用 Reduce 归并局部结果；"分解—计算—归并"。
  2. "移动计算而非移动数据"：数据量大、网络传输贵，因此把计算程序调度到数据所在的节点执行（数据本地性 locality），只传输小的中间结果。
  3. 简化编程模型、隐藏分布式细节：用户只需实现 map() 与 reduce() 两个函数，分布式存储、任务调度与监控、节点通信、负载均衡、故障处理（重试）全部由框架完成。
🔑 三个关键词：拆分（Map）— 归并（Reduce）— 就近计算（本地性）。若题目问"MapReduce 最大的优点"，答"编程模型简单、对海量数据高吞吐、可运行在廉价集群上、自动容错"。

二、主从结构与组成部分（识记）⭐

识记 MapReduce 的主从结构和组成部分。
主从结构（Master/Slave）：一个 JobTracker（主节点） + 多个 TaskTracker（从节点）。JobTracker 是全局唯一的"总管家"，TaskTracker 是"干活的工人"，两者通过心跳保持联系。
组成部分所属职责
Client 客户端提交端提交作业（打包 jar + 配置）、计算输入切片 InputSplit、监控并获取作业运行状态
JobTracker（MRv1 主节点）Master资源管理 + 作业/任务调度（全局）：分配任务、监控进度与状态、失败重启、维护 TaskTracker 心跳；不存数据
TaskTracker（MRv1 从节点）Slave执行 Map/Reduce 任务、管理本节点 CPU/内存槽位、定期向 JobTracker 发心跳并汇报任务进度与状态；启动 TaskRunner 子进程运行任务
Task 任务执行单元分 MapTask 与 ReduceTask 两类，一个 InputSplit 对应一个 MapTask
Job 配置文件描述指定输入/输出路径、map/reduce 类、分区函数、排序与组合、规约（Combiner）、Reduce 任务数等
HDFS存储存放输入数据、中间结果（本地磁盘）、最终输出（HDFS）
Map / Reduce 函数用户代码用户自定义的映射与归约逻辑
MRv2（On YARN）的对应变化（常考对比）：JobTracker 的职责被拆开——ResourceManager（全局资源管理与调度）＋ 每个作业一个 ApplicationMaster / MRAppMaster（该作业的任务调度、监控与失败处理）；TaskTracker → NodeManager（单节点资源管理，按 Container 分配）；资源单位抽象为 Container。好处：资源管理与计算框架解耦、支持多框架共享集群、JobTracker 压力被分摊、可扩展性大幅提升（可支持上千节点）。

三、工作流程：作业提交与任务执行（领会 / 简单应用）⭐

领会 处理过程、任务执行过程、任务进度与状态更新；简单应用 作业提交过程、任务执行过程。
MapReduce 处理过程总览（简答"MapReduce 工作流程"照此分步写）
（一）作业提交过程（MRv1·七步，简单应用要能默写）：
  1. 客户端调用 Job.submit() 把作业 jar 包、配置文件、切片信息提交（上传）到 HDFS 上的作业目录。
  2. JobTracker 收到通知，初始化作业：把作业加入调度队列，创建 JobInProgress 并读取切片信息。
  3. JobTracker 按调度策略（默认 FIFO）为作业分配 Map 任务与 Reduce 任务，确定任务数。
  4. TaskTracker 通过心跳领任务；领取前通过分布式缓存从 HDFS 下载作业程序（jar）与配置。
  5. TaskTracker 启动 TaskRunner 子进程执行任务（Map 优先，遵循数据本地性：本地节点 → 同机架 → 其他机架）。
  6. 任务运行中，TaskRunner 把进度与状态写入状态文件，TaskTracker 通过心跳汇报给 JobTracker；JobTracker 汇总后供客户端查询（job.waitForCompletion 轮询）。
  7. 作业完成：JobTracker 记录作业日志与统计信息（历史服务器可查），客户端收到成功/失败状态。
（二）Map 任务执行过程（六步）：①RecordReader 读取 InputSplit，逐条转成 <k1,v1>（行号→文本行）→ ②调用用户 map() 输出 <k2,v2> → ③写入环形内存缓冲区（mapreduce.task.io.sort.mb 默认 100MB，溢写阈值 0.8）→ ④达到阈值则分区（Partitioner，默认 Hash 取模）+ 快排 + （可选 Combiner 预聚合）溢写到本地磁盘（可多次溢写）→ ⑤合并（merge）多个溢写文件为一个分区且有序的最终输出文件 → ⑥把输出文件路径与分区信息报告给 TaskTracker/AM，等待 Reduce 拉取。
（三）Reduce 任务执行过程（五步）：①Copy/拉取（shuffle）：从各 Map 节点并行拉取属于本分区的中间数据（内存放不下则先溢写磁盘）→ ②归并排序 Merge：把多路已排序数据归并成按 key 有序 → ③Grouping 分组：同一 key 的 value 聚成一个列表 <k3, list(v3)> → ④调用用户 reduce() 归约输出 <k4,v4> → ⑤由 RecordWriter 写入 HDFS（默认生成 part-r-00000 等文件，Reduce 任务数 = 输出文件数）。
（四）任务进度与状态更新机制（领会）：Map 进度按读入/映射/溢写加权计算，Reduce 进度按拉取/排序/归约/写盘加权；TaskRunner 定期更新状态文件 → TaskTracker 心跳上报 → JobTracker 汇总为作业进度百分比。失败时 JobTracker 把任务重新调度到其他节点重试（默认尝试次数上限 mapreduce.map.maxattempts=4），超过则作业失败。
⚠️ 三个高频陷阱：①InputSplit 是逻辑切片，不是物理文件（一个 Split 对应一个 Map 任务，切片大小一般等于 HDFS 块大小 128M）；②中间结果不在 HDFS 上（存 TaskTracker 本地磁盘），只有输入/输出在 HDFS；③Reduce 任务数为 0 时没有 Shuffle 与 Reduce，Map 输出直接作为结果（相当于只做过滤/转换）。

四、计算过程详解：WordCount 逐步推演（综合应用）⭐⭐

综合应用 MapReduce 计算过程分析。
题目设定：两个输入分片，Reduce 任务数 = 2，分区规则 key.hashCode() % 2（此处简化为"首字母在 a~m 归 0、n~z 归 1"）。求词频。
阶段分片 0（内容：hello world hello）分片 1（内容：world big data）
① 输入 <k1,v1><0, "hello world hello"><0, "world big data">
② Map 输出 <k2,v2><hello,1> <world,1> <hello,1><world,1> <big,1> <data,1>
③ 分区 Partitionhello→0，world→1world→1，big→0，data→0
④ 排序 + Combiner（本地预聚合）分区0：<hello,2>；分区1：<world,1>分区0：<big,1> <data,1>；分区1：<world,1>
⑤ Shuffle 拉取 + 归并（按 key 有序）Reduce 0 收到：<big,[1]> <data,[1]> <hello,[2]>　Reduce 1 收到：<hello? 无> <world,[1,1]>
⑥ Reduce 输出 <k4,v4><big,1> <data,1> <hello,2>（part-r-00000）；<world,2>（part-r-00001）
答题模板（拿分四步，写全就不扣分）：① 写出每个分片的 Map 输出（键值对列表）→ ② 标明分区归属与排序结果（可写 Combiner 前后两版）→ ③ 写出Reduce 端拉取并归并后的分组<key, [values]> → ④ 给出最终输出与所在文件（part-r-0000x）。
变式练手（同套路）：①求最大值——map 输出 <"max", v>，reduce 对列表取最大；②倒排索引——map 输出 <word, docId>，reduce 收集 docId 集合；③词共现——map 输出 <(w1,w2), 1>；④Join——map 端把两表按连接键打标签输出，reduce 端按标签分桶再组合。注意：这些题的得分点都在②③步的"分组"是否写对。

五、使用案例与适用边界（领会）

典型使用案例：①词频统计 WordCount（入门例）；②倒排索引（搜索引擎建库）；③分布式排序 / 二次排序；④矩阵乘法；⑤共现矩阵与关联分析；⑥K-Means 聚类（迭代式，每轮一个 MR）；⑦数据去重、抽样、统计聚合（PV/UV）；⑧文本压缩与 ETL。
适用与不适用（简答）：✔ 适合离线、批处理、高吞吐、一次读大量数据、计算密集的场景；✘ 不适合实时/流式计算（作业启动与磁盘开销大、延迟高）、迭代式计算（每轮都要读写磁盘、中间结果无法复用）、交互式查询、依赖全局共享状态的算法。

六、Spark 概述：优势与架构（教材 4.7 节）⭐

领会 Spark 的优势、Spark 的架构。
是什么：Spark 是 UC Berkeley AMPLab 开源的基于内存计算的、快速通用的分布式大数据处理引擎（MapReduce 的改进/替代者），提供 Java/Scala/Python/R API，自带一体化组件：Spark SQL（结构化查询）、MLlib（机器学习）、GraphX（图计算）、Structured Streaming（流计算）。
Spark 的优势（简答·六条）：
  1. 运行速度快（内存计算）：中间结果放内存而非落盘，迭代计算比 Hadoop MapReduce 快 10～100 倍。
  2. 使用 Java/Scala/Python/R 多语言 API，并提供交互式 Shell，开发效率高。
  3. 通用性/一体化：同一引擎支持 SQL、机器学习、图计算、流处理，减少系统割裂。
  4. 运行模式灵活：可独立（Standalone）运行，也可跑在 YARN、Mesos、K8s 上，可读取 HDFS、HBase、Hive、MySQL、S3 等多种数据源。
  5. 与 Hadoop 生态兼容，可直接复用 HDFS 与 YARN。
  6. RDD 容错机制高效：靠血缘（Lineage）重算丢失分区，不必像副本那样复制数据。
核心抽象 RDD（弹性分布式数据集）——名词解释常考：一个只读、可分区、可并行计算的分布式数据集合，可常驻内存；通过转换算子（transformation，惰性）生成新 RDD，通过行动算子（action）触发真正计算；对上游 RDD 的依赖关系构成 DAG，故障时按血缘重算恢复。
Spark 架构（主从 + 三层调度概念）：
概念/组件含义
Application包含 Driver 与集群上多个 Executor 的用户程序
Driver（驱动程序）运行 main()、创建 SparkContext，负责把 RDD 操作构建 DAG → 划分 Stage → 提交任务 → 收集结果（内含 DAGScheduler 与 TaskScheduler）
Cluster Manager集群资源管理（Standalone Master / YARN ResourceManager / Mesos Master）
Worker Node工作节点，保存本节点 CPU/内存资源，接收 Cluster Manager 分配、启动 Executor
Executor每个节点上的执行进程，负责运行 Task、管理内存与缓存数据，向 Driver 汇报状态
Job / Stage / Task一个 action 触发一个 Job；Job 按 RDD 依赖（宽依赖/Shuffle 为界）拆成多个 Stage；Stage 内按分区并行拆成多个 Task（最小执行单元）
Spark vs MapReduce（对比简答）：①中间结果：MR 落盘 vs Spark 尽量驻留内存；②计算模型：MR 只有 Map/Reduce 两步、复杂任务需串联多个作业 vs Spark 提供 DAG 多算子一次表达；③迭代/交互/流式：MR 弱 vs Spark 强；④容错：MR 靠重跑任务/副本 vs Spark 靠 RDD 血缘重算；⑤语言与生态：MR 主要 Java vs Spark 多语言 + SQL/ML/Graph/Streaming 一体；⑥磁盘 I/O 与延迟：MR 高 vs Spark 低。但 Spark 内存开销大、对内存不足的大规模 shuffle 场景不一定优于 MR，且 MR 更成熟稳定、容错粒度更粗但更稳。
⚠️ 易错：Spark 快不是因为"用了更多的机器"，而是避免中间结果落盘 + DAG 优化执行；宽依赖（shuffle 依赖）才切 Stage，窄依赖（map 端融合）在同一 Stage 内流水线执行。

七、本章速记小结

  1. 设计思想三条：分而治之、移动计算而非移动数据、简化编程模型（只写 map/reduce）。
  2. 主从组成：Client、JobTracker、TaskTracker、Task、配置、HDFS；MRv2 换成 RM + NM + AM + Container。
  3. 流程：提交七步；Map 六步（环形缓冲 100M、溢写阈值 0.8、分区排序合并）；Reduce 五步（拉取—归并—分组—归约—写 HDFS）。
  4. 计算过程：WordCount 表格里 ②Map 输出 → ③分区 → ⑤分组 是全部得分点。
  5. 边界：MR 适合离线批处理，不适合实时、迭代、交互。
  6. Spark：内存计算 + RDD（只读、可分区、惰性、血缘容错）+ DAG/Stage/Task；六大优势与 MR 六项对比。
🎯 6 学时分配：①设计思想 + 组成 1 学时；②工作流程 2 学时（提交/Map/Reduce 三段必须能分步书写）；③计算过程推演 1.5 学时（亲手算 WordCount + 一个变式）；④使用案例 0.5 学时；⑤Spark 1 学时。⚠️ 教材 4.6、4.8 不考，Spark 只看 4.7 节。
